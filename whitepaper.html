PayStream

Onchain Payroll & Salary Streaming Protocol

Network: BOT Chain (Chain ID 677)
Stack: Solidity ^0.8.20 · ethers.js v6 · Vanilla JS
Published: November 2026
Abstract. PayStream is a non-custodial, on-chain payroll protocol built on BOT Chain. It enables organizations and DAOs to fund payroll treasuries, register employees, and configure salary streams. Employees accrue salary continuously and claim it on-demand via a blockchain transaction. No automatic execution occurs — all state changes require explicit on-chain transactions. This document describes the protocol architecture, payroll accounting, payment schedules, token support, and security model.

1. Executive Summary

PayStream replaces traditional payroll infrastructure with smart contracts. Employers deposit funds once; employees accrue salary proportionally over time and withdraw whenever they choose. All payroll records — deposits, streams, claims — are permanently on-chain.

  • Non-custodial. Funds are held by the PayrollStreamManager contract. No third party controls them.
  • Proportional accrual. Salary accrues continuously by the second, not in discrete lump sums.
  • Claim-based withdrawals. Employees trigger claims explicitly. No scheduled automatic transfers.
  • Employer controls. Streams can be paused, terminated, or salary-adjusted at any time — all recorded on-chain with transparent effective dates.
  • BOT and ERC-20 support. Payroll can be denominated in native BOT or any ERC-20 token (such as USDT).

3. Payroll Accounting

3.1 Accrual Model

Salary accrues continuously and proportionally. For any active stream, the pending accrual at any moment is:

pending = salaryPerPeriod × (block.timestamp − lastClaimTime) / periodDuration

Example: an employee earning 2,000 BOT per week who last claimed 3.5 days ago has accrued approximately 1,000 BOT.

The accrual is calculated lazily — it is not stored or updated on every block. It is computed on-demand when getClaimable() is called or when any state-changing function touches the stream.

3.2 Claim Mechanics

Claiming follows strict checks-effects-interactions ordering to prevent reentrancy and double-claiming:

function claimSalary(uint256 streamId) external nonReentrant {
  // 1. Accrue pending into accruedBalance
  _accrue(streamId);
  uint256 claimable = accruedBalance[streamId];

  // CHECKS
  require(claimable > 0, "Nothing to claim");
  require(orgTreasury[orgId][token] >= claimable, "Insufficient funds");

  // EFFECTS (state updated before any transfer)
  accruedBalance[streamId] = 0;
  lastClaimTime = block.timestamp;
  totalPaid += claimable;
  orgTreasury[orgId][token] -= claimable;

  // INTERACTIONS (transfer last)
  transfer(employee, claimable);
}
⚠️ No Automatic Execution PayStream contracts do not and cannot execute automatically at future dates. Employees must submit a transaction to trigger a claim. Employers must submit transactions for all administrative actions. This is a fundamental property of EVM smart contracts.

3.3 Salary Modification

When an employer updates a salary, the pending accrual under the old rate is captured first:

  1. _accrue(streamId) is called — this banks the pending amount at the current rate into accruedBalance.
  2. salaryPerPeriod is updated to the new value.
  3. Future accrual uses the new rate from this point forward.

This ensures employees are paid correctly for time worked at the old rate up to the modification timestamp.

4. Payment Schedules

PayStream supports any periodDuration of at least 1 day. The standard options are:

SchedulePeriod (seconds)Example Salary
Weekly604,8002,000 BOT/week = ~285.7 BOT/day
Bi-Weekly1,209,6004,000 BOT/bi-week = ~285.7 BOT/day
Monthly (30-day)2,592,0008,000 BOT/month = ~266.7 BOT/day
CustomAny ≥ 86,400Configurable by employer

Because accrual is proportional, the salary is effectively the same daily rate regardless of which period option is selected — the period only affects how the nominal salary figure is stated, not what the employee earns per second.

5. Token Support

🚫 Fee-on-Transfer Tokens Tokens that deduct a fee on each transfer may credit less to the recipient than the stream's salary amount specifies. PayStream v1.0 does not adjust for this. Verify token behavior before configuring a stream with non-standard ERC-20 tokens.

Each stream is denominated in a single token set at creation. Changing the token requires terminating the existing stream and creating a new one.

6. Treasury Management

Each organization has a per-token treasury balance tracked in orgTreasury[orgId][token]. This balance covers all active streams for that organization in that token.

Funding Responsibility

Employers are responsible for keeping the treasury funded. If the treasury balance falls below the claimable amount for a stream, that claim will revert with "Insufficient payroll funds". The employee's accrued balance is preserved and can be claimed once the employer tops up the treasury.

Underfunding Detection

The frontend reads getTreasuryBalance(orgId, token) and calculates projected run-out time based on total active stream accrual rates. A warning is displayed when the treasury covers less than 30 days of combined payroll.

Treasury Withdrawal

Employers can withdraw unallocated treasury funds via withdrawTreasury(orgId, token, amount). This does not check accrued employee balances — it is the employer's responsibility to leave sufficient funds to cover accrued and near-term payroll.

7. Employee Lifecycle

addEmployee() ──► Active │ ┌──────────┼──────────┐ ▼ ▼ ▼ setStatus │ setStatus (Paused) [stream] (Terminated) │ running │ ▼ ▼ Paused Terminated │ (final state) ▼ setStatus (Active) ──► stream resumes

When an employee is paused or terminated, their payroll stream status is updated separately via setStreamStatus(). The employee registry status and stream status are independent — this allows an employer to pause a stream without removing the employee record.

Termination is final. A terminated employee's stream stops accruing. Any balance already accrued remains claimable.
